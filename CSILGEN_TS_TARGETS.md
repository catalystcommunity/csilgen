# csilgen — TypeScript client & server targets

**Status:** implemented in `csilgen` (`wasm/csilgen-typescript-generator/`). The notes below record where the shipped behavior differs from this original brief.

## Implementation notes (as built)

- **Four targets, one generator.** Rather than two new crates, the existing `csilgen-typescript-generator` wasm dispatches on `config.target`:
  - `typescript` — emits all three files (types + client + server)
  - `typescript-typesonly` — `types.gen.ts` only
  - `typescript-client` — `types.gen.ts` + `client.gen.ts`
  - `typescript-server` — `types.gen.ts` + `server.gen.ts`
- **Client/server always emit their types.** `typescript-client` and `typescript-server` emit `types.gen.ts` alongside their file and import from it (default module `./types.gen`). There is no separate types-only step required.
- **CLI changes were required** (the brief assumed none): the target→generator map and `--target` help text in `crates/csilgen-cli` were extended for the three new target names.
- **Doc comments use `;;;`, not `//`.** CSIL comments are `;`/`;;`; documentation comments are `;;;` and attach to the following rule/field/operation. They are surfaced as JSDoc on the corresponding TypeScript output.
- **`ServiceError`** is emitted into `types.gen.ts` as `{ code: number; message: string }` whenever the spec declares services (unless the spec defines its own `ServiceError`). A top-level `/ ServiceError` in an operation's output is treated as a thrown error and stripped from the method's return type; other domain-error union members are preserved as returned values.
- **Options are flat keys** (the CSIL `options{}` block is flat): `client_types_module` (default `./types.gen`) and `aggregate_class_name` (default `ApiClient`; empty string disables the aggregate class). The brief's nested `options.ts_client.*` is not used.
- **Bidirectional (`<->`) and reverse (`<-`) operations** now have a real handler+router emission, applied consistently across all generators (TS/Rust/Go/Python). Generators emit *shapes and routing only* — never the wire. The TS generator additionally accepts `ts_bidirectional_transport: "connection"` (default, push-based) or `"rpc"` (degraded poll model) plus an `ts_ws_base_url` hint constant. These options are TypeScript-only; the other generators ignore them. See `csil-spec.md` "Operation Directions" for the cross-generator contract.

## Original brief (for reference)

## Context

[csilgen](https://github.com/catalystcommunity/csilgen) is the CSIL (CBOR Service Interface Language) code generator. It parses `*.csil` files (a CDDL-derived IDL) into a `CsilSpec` AST and dispatches generation to per-target WASM modules discovered at runtime from built-ins plus `~/.csilgen/generators/csilgen-<target>.wasm`.

**Existing targets:** `json`, `rust`, `python`, `typescript` (types only), `openapi`, `go`.

The Longhouse SolidJS client at `client/` needs **typed call sites** for the API defined in `csil/longhouse.csil`. The existing `typescript` target emits interfaces — useful, but stops short of generating the functions that hit the wire. This brief specifies two new targets to fill the gap:

- **`typescript-client`** — typed `fetch`-based client functions, one per service method. **Required for this project.**
- **`typescript-server`** — framework-agnostic handler interfaces + a dispatch helper. **Not used by this project, but specified for parity and to keep the generator family symmetric.** Implementers can ship Express/Hono/Fastify adapters separately if they want.

Both targets consume the output of the existing `typescript` target for their type imports — they do not duplicate type emission.

## Architecture

Follow the existing pattern in `crates/core_generators/csilgen-typescript`:

- New crates: `crates/core_generators/csilgen-typescript-client` and `crates/core_generators/csilgen-typescript-server`.
- Each is a `cdylib` exporting `get_metadata`, `allocate`, `deallocate`, and `generate(input_ptr, input_len) -> *mut u8`.
- Input is JSON-serialized `WasmGeneratorInput`; output is `WasmGeneratorOutput`.
- Built artifact lands at `~/.csilgen/generators/csilgen-typescript-client.wasm` (and `-server.wasm`).
- Invoked as `csilgen generate --input spec.csil --target typescript-client --output ./gen/`.

No changes to the csilgen CLI or core needed.

## `typescript-client` — output specification

### File layout

Emit a single file: `client.gen.ts`. One file keeps imports simple for the SPA bundler and matches the existing `typescript` target's single-file output.

### Required header

```ts
// Code generated by csilgen. DO NOT EDIT.
// Source: <input filename>
// Target: typescript-client
```

### Imports

The client file imports type names from the companion `typescript` target's output. Configurable via a generator option `client_types_module` (defaults to `"./types.gen"`):

```ts
import type {
  LoginRequest, LoginResponse, ServiceError,
  House, HouseID, Member, MemberID,
  // ... all referenced types
} from "./types.gen";
```

### Type mapping (CSIL → TypeScript)

| CSIL | TypeScript |
|---|---|
| `text` | `string` |
| `int` (signed) | `number` |
| `uint` | `number` |
| `bool` | `boolean` |
| `bytes` | `Uint8Array` |
| `[* T]` (repeated) | `T[]` |
| `? field: T` (optional) | `field?: T` |
| `T / U` (choice/union) | `T \| U` |
| `Timestamp` (RFC3339) | `string` (RFC3339, callers/transport responsible) |
| Custom type aliases (`type HouseID = text`) | `type HouseID = string` (already done by types target) |

The client target **must not redefine types** — it imports them from the types target.

### Transport interface

The generated client is **transport-agnostic**. It calls into a user-supplied `Transport` interface. The Longhouse repo ships its own implementation in `client/src/transport/cbor.ts`; other consumers can plug JSON or anything else.

```ts
export interface ServiceTransport {
  call<TReq, TRes>(
    service: string,        // e.g. "auth", "house"
    method: string,         // e.g. "Login", "ListMembers"
    req: TReq,
    opts?: { signal?: AbortSignal },
  ): Promise<TRes>;
}
```

The transport is responsible for:
- Choosing the encoding (CBOR or JSON; content-type negotiated by the implementation).
- Building the URL (the generator emits `service` and `method` strings; the transport maps them to a path or a single endpoint).
- Sending auth (cookie via `credentials: "include"`, or `Authorization` header — transport's call).
- Decoding the response and raising `ServiceError`-shaped errors.

The generator emits no URL strings. It does not know what wire format the transport uses. This is intentional: the same generated client serves the SPA (CBOR), a Node tooling script (JSON over HTTPS), and a test fake (in-memory).

### Generated client shape

Two patterns are acceptable; the client target picks one and is consistent. **Recommended: namespaced classes per service.**

```ts
// from: service Auth { Login(LoginRequest) -> LoginResponse / ServiceError }
//       service Member { ListMembers(...) -> ListMembersResponse / ServiceError }
export class AuthClient {
  constructor(private readonly t: ServiceTransport) {}
  login(req: LoginRequest, opts?: { signal?: AbortSignal }): Promise<LoginResponse> {
    return this.t.call<LoginRequest, LoginResponse>("auth", "Login", req, opts);
  }
}
export class MemberClient {
  constructor(private readonly t: ServiceTransport) {}
  listMembers(req: ListMembersRequest, opts?: { signal?: AbortSignal }): Promise<ListMembersResponse> {
    return this.t.call<ListMembersRequest, ListMembersResponse>("member", "ListMembers", req, opts);
  }
  // ... one method per service operation, camelCased
}

// convenience aggregate so consumers can compose if they want
export class LonghouseClient {
  readonly auth:   AuthClient;
  readonly member: MemberClient;
  // ... one field per service
  constructor(t: ServiceTransport) {
    this.auth   = new AuthClient(t);
    this.member = new MemberClient(t);
  }
}
```

### Method naming

- Method name on the class: **camelCase** of the CSIL operation name (`Login` → `login`, `ListMembers` → `listMembers`, `GetMemberByIdentity` → `getMemberByIdentity`).
- Service strings passed to transport: **lowercase** of the CSIL service name (`AuthService` → `"auth"`, `MemberService` → `"member"`). Strip the `Service` suffix.
- Method strings passed to transport: **PascalCase as written in CSIL** (`Login`, `ListMembers`). The Go server uses these as method dispatch keys; keep them stable.

### Error handling

Errors are throws, not return values. The transport detects a `ServiceError` response and throws an instance of a class the transport defines. The generated client annotates throws in JSDoc:

```ts
/**
 * @throws {ServiceError} when the API returns an error response
 * @throws transport errors (network, timeout) — defined by the transport implementation
 */
login(req: LoginRequest): Promise<LoginResponse>;
```

The generator does not import or define error classes — that's the transport's concern.

### Optional fields

CSIL optional fields (`? display_name: text`) emit as `display_name?: string` in types (existing target behavior). The client target does not transform these — the request type is passed through to the transport.

### Generator options

The `typescript-client` target accepts these options under `options.ts_client.*` in the CSIL file:

| Option | Default | Meaning |
|---|---|---|
| `client_types_module` | `"./types.gen"` | Import path for the companion types file. |
| `aggregate_class_name` | `"LonghouseClient"` (or derived from package name) | Name of the umbrella class composing all per-service clients. Set to `null` to disable aggregate emission. |
| `header` | (none) | Extra lines to inject at the top of the file. |

## `typescript-server` — output specification

### File layout

Single file: `server.gen.ts`.

### Generated shape

Emit one interface per service that the server implements, plus a `dispatch` helper that maps `(service, method, requestBytes)` to a handler call. No framework binding — adapters (Express, Hono, Fastify) are written by users.

```ts
// from: service Auth { Login(LoginRequest) -> LoginResponse / ServiceError }
export interface AuthHandlers {
  login(req: LoginRequest, ctx: RequestContext): Promise<LoginResponse>;
}
export interface MemberHandlers {
  listMembers(req: ListMembersRequest, ctx: RequestContext): Promise<ListMembersResponse>;
  // ... one method per operation
}

// the consumer-defined context carries auth, request id, etc.
// generator emits this as an opaque generic; transport defines its shape.
export interface RequestContext { /* opaque — user-defined */ }

export interface Codec {
  decode<T>(bytes: Uint8Array): T;
  encode(value: unknown): Uint8Array;
}

export interface ServerHandlers {
  auth:   AuthHandlers;
  member: MemberHandlers;
  // ... one per service
}

/**
 * Dispatch a single call. Caller decodes service+method from the wire,
 * passes raw request bytes + a codec, and gets raw response bytes back.
 * Throws ServiceError for protocol errors.
 */
export async function dispatch(
  handlers: ServerHandlers,
  codec: Codec,
  service: string,
  method: string,
  reqBytes: Uint8Array,
  ctx: RequestContext,
): Promise<Uint8Array> {
  // switch on (service, method) → handler[service][method](codec.decode(reqBytes), ctx)
  // → codec.encode(result)
}
```

### Why no framework

A generated HTTP adapter has to make a transport call — path-per-method? single endpoint with method-in-body? Authorization where? — that's a project-level decision, not a generator's. The dispatch helper keeps the generator transport-agnostic; users write a ~10-line Express handler that calls `dispatch`.

## Acceptance criteria

The target ships when:

1. **Generator builds.** `cargo build -p csilgen-typescript-client --target wasm32-wasi --release` produces a `.wasm` that csilgen discovers and runs.
2. **Output compiles.** Running the generator against `longhouse.csil` produces `client.gen.ts` that passes `tsc --noEmit --strict` against the existing `types.gen.ts` and the `Transport` interface above.
3. **Round-trip works.** A unit test wires a fake transport, calls `client.auth.login({signed_assertion: "x"})`, and asserts the transport saw `service: "auth"`, `method: "Login"`, request body matching `LoginRequest`. Equivalent test for `typescript-server` dispatching to a fake handler.
4. **No type imports leak.** `client.gen.ts` imports only `type`-only imports (so the bundler can drop them at build time). Use `import type { ... }` syntax.
5. **Determinism.** Two runs against the same input produce byte-identical output. Order interface emission by service name (alphabetical) then method name (CSIL order).
6. **Comments preserved.** If the CSIL spec has `//` line comments on a service or method, emit those as JSDoc on the generated method.
7. **Strict TypeScript clean.** No `any`. No `@ts-ignore`. No unused imports.

## Out of scope

- HTTP path schemes, URL templating, REST verb mapping — entirely the transport's job.
- Authentication helpers, retry logic, request batching, request ID injection — middleware concerns the consumer composes around the transport.
- React/Solid/Vue framework bindings (`useTask()` hooks, etc.). The consumer wraps the generated client in their own framework primitives.
- Streaming / bidirectional service operations. Defer until needed; the current `longhouse.csil` is all unidirectional request/response.
- A test harness or mock generator. Consumers write fakes manually using the same `ServiceTransport` interface.

## Reference: how Longhouse will consume this

```ts
// client/src/transport/cbor.ts (already exists, will be extended)
export class CborHttpTransport implements ServiceTransport {
  constructor(private readonly baseUrl: string) {}
  async call<TReq, TRes>(service: string, method: string, req: TReq, opts?): Promise<TRes> {
    const res = await fetch(`${this.baseUrl}/api/v1/${service}/${method}`, {
      method: "POST",
      credentials: "include",
      headers: { "content-type": "application/cbor", accept: "application/cbor" },
      body: encoder.encode(req),
      signal: opts?.signal,
    });
    // handle ServiceError shape → throw CsilError(code, message)
    // decode response body → return as TRes
  }
}

// client/src/data/repo.ts (refactor on adoption)
const client = new LonghouseClient(new CborHttpTransport("/api"));
export const repo: Repo = {
  listTasks:    () => client.task.listTasks({ /* ... */ }),
  listMembers:  () => client.member.listMembers({ /* ... */ }),
  // ...
};
```

When the API server still speaks JSON (current state), swap in a `JsonHttpTransport` with the same `ServiceTransport` interface — generated code doesn't change.
